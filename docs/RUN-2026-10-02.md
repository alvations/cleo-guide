## 2a. SOURCE MIX — every map draws from the FULL source palette (user instruction)
Each city's places must come from a deliberate mix, not just one channel:
- **Credible editorial of record** — national/regional press, city magazines, food critics, Michelin/James Beard/
  UNESCO/national-heritage bodies, official tourism boards.
- **Viral & creator sources** — **YouTubers, TikTokers, Instagram creators, travel bloggers and vloggers** with a
  verifiably large following and a real beat for this city/country, plus a *specific findable* video/post/article
  naming the place. Search for them explicitly every wave (e.g. `"<city>" food tour youtube`, `"<city>" tiktok
  viral <dish>`, `<city> 必食 youtuber`, `<city> travel vlog hidden gems`, `best <city> food blog`).
- **Notable travel sites** — Lonely Planet, Time Out, Atlas Obscura, Condé Nast Traveler, CNN/BBC/NatGeo Travel,
  Eater/Infatuation, Rick Steves, japan-guide etc. — whichever are notable for that country.
- **Local recommendation** — locals' picks from community press, neighbourhood outlets, city subreddits/forums and
  local creators (corroborating only; a lone forum comment never pins a place).
- **Start from the registry:** read `data/sources.json` → `nationalCreators` + `sourceTypes` (global) and the
  city/country entries already there (e.g. the Belgian/Singapore/Japan briefs' palettes); reuse those creators and
  outlets where they cover your city, then ADD the new ones you vet (with a `credible` rationale and follower
  scale) so the registry grows per country and globally. Record creators in `CREATORS_<tag>.json`
  (`{creators:[{key,name,platform,handle,url,scale,niche,credible}], attach:[{place,creatorKey,url}], rejected:[…]}`).
- **The vetting bar does not drop:** a creator is ONE corroborating source, never institutional; reject anonymous
  accounts, unverifiable follower counts, SEO farms and AI listicles; ≥2 credible sources (or a lone institution)
  per place still applies. Report per wave how many places each channel contributed, so the mix is auditable in AUDIT.md.

**Key hygiene (lone-authority keys).** `JAMESBEARD` / `MICHELIN*` / `UNESCO` / `NPS` / `BUNKACHO` mean the
institution's AWARD or DESIGNATION only. Editorial content from those bodies (e.g. James Beard "Ask a Chef"
interviews, Michelin magazine features) uses its own key — `JBF_EDITORIAL`, `MICHELIN_EDITORIAL` — which counts
as ONE ordinary source, never a lone authority. (Gap found by the Madison agent, 2026-10-02.)

## 3. Concurrency rules (non-negotiable)
```bash
LOCK=/home/user/cleo-guide/.git/cleo-shared.lock
flock -w 3600 $LOCK <command>
```
- Write freely ONLY inside your own research dir (or, for Singapore, only YOUR tagged files in the shared dir).
- EVERY command that writes a shared file runs under the lock: `tools/rebuild-city.py … --build` (writes
  `data/geocodes.json`, `data/sources.json`, `docs/GEOCODE-BACKLOG.md`), any edit to `index.html`, a country hub,
  `data/countries.json`, `docs/CITIES.md`, `tools/*`, and every `git add/commit/push`.
- For shared-file edits use a short python/sed edit run under `flock` that re-reads the file inside the lock and
  changes only your part — never Write a whole shared file from a stale copy. Hubs/index carry
  `<!-- CARD:<key> --> … <!-- /CARD:<key> -->` markers: edit ONLY your own card.
- Never edit another city's files. Helper scripts/temp files go in YOUR research dir with a city-unique name (e.g. `data/<city>-research/_<city>_add.py`) — the session scratchpad is shared by every agent and generic names (`add.py`) get clobbered. Never run `git add -A`/`git add .`; add explicit paths.
- Run `cd tools && npm run validate && npm test` under the lock before each commit; if a failure is caused by
  another agent's in-progress city, note it and commit your own paths anyway only if YOUR pages pass.

## 5b. RESUMABILITY — survive token limits, context compaction and container restarts (user instruction)
Assume you can be cut off at ANY moment (token limit, compaction, rate limit, container reclaim). So:
1. **Checkpoint before you spend.** At the start of every wave write the plan into `RESUME.md` under
   `## In-flight wave` (wave tag, area, files it will write, queries still to run). At the end, move it to
   `## State` with the outcome and clear `In-flight wave`. A relaunched agent finishes an in-flight wave first.
2. **Write as you go, not at the end.** Append each verified place to its `FOOD_*/SIGHTS_*` file as soon as it is
   verified (small batches of ~10); append each geocode result to `geo/_geoout_*.json` immediately. Never hold
   a whole wave in memory.
3. **Commit + push after every batch** (protocol §4) — uncommitted work is lost work. Max ~30 minutes between pushes.
4. **`RESUME.md` must always answer:** what's done (counts per area vs target), what's half-done (the in-flight
   wave + which queries remain), what's next (ordered), which files hold what, and the exact commands to continue
   (`python3 tools/density.py <key>`, `flock … python3 tools/rebuild-city.py <key> --build`).
5. **Relaunch contract:** the orchestrator relaunches a stopped agent with the same task prompt; the agent reads
   this protocol → its `RESUME.md` → `AUDIT.md` tail → `git log --oneline -20 -- data/<city>-research` and
   continues from there, never redoing a committed wave and never duplicating a place already in the files.
